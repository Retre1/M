# Анализ: метрики прогонов 1–6 недействительны

> Дата анализа: 2026-08-08
> Предмет: [[../runs/CHRONOLOGY_RUNS_1-6|хронология прогонов 1–6]], `backtest_results.json`,
> `AUDIT_REPORT.md`, ветки `main` и `v2.0-quantum-hybrid`
> Статус: **действующий** — до исправления измерителя выводы хронологии применять нельзя

---

## Краткая суть

Шесть прогонов (18–19 апреля 2026, ~26 часов на A100) оценивались метриками
`sharpe` и `profit_factor`, которые считаются **по ряду наград эпизодов**, а не
по реализованному PnL. Как следствие:

1. `PF = 0` во всех шести прогонах — арифметическое тождество, а не поведение агента.
2. `sharpe` порядка −52 … −700 000 не является финансовым коэффициентом Шарпа.
3. Улучшение «−147 → −58 → −52» между прогонами во многом отражает
   перемасштабирование самой награды, а не улучшение политики.
4. Единственная сопоставимая финансовая метрика (OOS profit factor) за тот же
   период **ухудшилась**: 0.957 → 0.736.

Отдельно обнаружено, что экспериментальная история и исправления аудита
находятся на **разных ветках**, и ни одна из них не содержит и то, и другое
(см. [§5](#5-два-разошедшихся-контура-разработки)).

---

## 1. `profit_factor` ≡ 0 по построению

`src/apexfx/training/trainer_v2.py` (ветка `v2.0-quantum-hybrid`, строки 161–164;
снимок — `src/_v2_dump/trainer_v2.py`):

```python
gains  = rewards[rewards > 0].sum()
losses = abs(rewards[rewards < 0].sum())
metrics["profit_factor"] = float(gains / max(losses, 1e-8))
```

`rewards` — массив **суммарных наград эпизодов** (`self._episode_rewards[-100:]`),
не PnL сделок.

Во всех шести прогонах `ep_rew_mean` отрицателен:

| Прогон | `ep_rew_mean` |
|---|---:|
| 1–3 | −2646 … −2813 |
| 4 | −1758 |
| 5 | −82 … −249 |
| 6 | −96 … −125 |

Ни один эпизод не дал положительной суммарной награды → `rewards[rewards > 0]`
пуст → `gains = 0` → **`PF = 0.0` независимо от торгового поведения**.

**Последствие серьёзнее самой метрики.** `MultiMetricEarlyStopConfig`
использует AND-логику с участием `profit_factor`. Метрика, тождественно равная
нулю, никогда «не улучшается» → постоянный сигнал stall → стадии обрывались на
18–27 % бюджета. Run 2 — ровно этот сценарий.

В хронологии это зафиксировано как «Открытая проблема #1» с гипотезой о
некорректной агрегации `n_episodes` при `n_envs=16`. Настоящая причина — строка
выше.

## 2. `sharpe` не является коэффициентом Шарпа

`trainer_v2.py:155-159`:

```python
if len(rewards) > 1 and np.std(rewards) > 0:
    metrics["sharpe"] = float(np.mean(rewards) / np.std(rewards) * np.sqrt(252))
```

Это отношение среднего к стандартному отклонению **по ряду наград**. Финансовый
Шарп считается по ряду доходностей и не может принимать значения порядка
−700 000 — сама величина доказывает, что измеряется другая сущность.

Практический вред: по критерию `best_sharpe` отбирались чекпоинты для
сохранения и последующей OOS-оценки (`CheckpointManager.get_best_model_path`,
`get_warm_start_path` — по умолчанию `criterion="sharpe"`). То есть «лучшая
модель» выбиралась по показателю без финансового смысла.

## 3. Межпрогонное сравнение некорректно

`mean/std` по ряду наград напрямую зависит от масштаба и состава награды. Между
прогонами эти веса менялись:

| Прогон | Изменение весов награды |
|---|---|
| 5 | `inactivity_weight` 0.0002 → 0.00005 (÷4), `realized_pnl_weight` 10000 → 2000 (÷5), `reward_clip` 30 → 50 |
| 6 | `realized_pnl_weight` 2000 → 4000 (×2) |

Меняя веса, меняем метрику, не меняя политику. Поэтому ряд «best Sharpe»
−147 (Run 3) → −58 (Run 5) → −52 (Run 6) **не является рядом сопоставимых
величин**, и вывод «Run 6 — лучший прогон» из него не следует.

## 4. Сопоставимая метрика движется в обратную сторону

OOS profit factor считается по реальным сделкам и сравним между прогонами:

| | Run 3 (баг награды активен) | Run 5 (баг исправлен) |
|---|---:|---:|
| OOS PF | **0.957** | **0.736** |
| Win rate | 44.55 % | 35.76 % |
| R:R (avg win / avg loss) | 1.19 | 1.32 |
| Безубыточный WR | 45.7 % | 43.1 % |
| **Дефицит до безубытка** | **1.1 п.п.** | **7.3 п.п.** |

Проверка арифметики Run 5: при WR = 35.76 %, avg win = $0.226, avg loss = $0.171

```
PF = (0.3576 × 0.226) / (0.6424 × 0.171) = 0.736 ✓ совпадает с отчётом
безубыточный WR = 1 / (1 + 1.322) = 43.1 %
```

Заголовочная метрика «улучшилась» втрое, реальная ухудшилась, разрыв до
безубытка вырос с 1 до 7 процентных пунктов.

### 4.1. Результат Run 5 статистически невесом

- Gross profit **$13.30**, gross loss **$18.07**, net **−$4.77** на $100 000
- Средний нотионал сделки ~**$50** = **0.05 %** капитала
- Max drawdown **$7.9** = **0.0079 %**

Это не «почти безубыток», а отсутствие экспозиции. При таком размере позиций из
165 сделок нельзя заключить ни наличия, ни отсутствия edge — результат
неотличим от шума.

## 5. Два разошедшихся контура разработки

Все шесть прогонов выполнены на ветке `v2.0-quantum-hybrid`, а не на `main`.
Ветки разошлись 2026-04-07 от `ce391a0`: **20 коммитов только в `main`,
24 только в `v2.0-quantum-hybrid`**.

| | `v2.0-quantum-hybrid` @ `a7b611e` | `main` @ `1f2a549` |
|---|---|---|
| Прогоны обучения | Все 6 (18–19 апр) | **Ни одного** |
| Разблокировка `RARAReward_v5` (`e856a7c`) | ✅ | ❌ класса нет |
| Настройки Run 6 (`dbc5bd6`, `a7b611e`) | ✅ | ❌ |
| Фиксы аудита: tanh-насыщение, `training_mode`, NaN-safety | ❌ | ✅ (24–25 апр) |
| `trainer_v2`, `curriculum_v2`, `reward_v5` | ✅ | ❌ |

**Ни одна ветка не содержит одновременно фиксы прогонов и фиксы аудита.**

Главное достижение серии — недостающая ветка `isinstance(RARAReward_v5)` в
`forex_env.step()`, стоившая трёх прогонов, — на `main` неприменима: класса
`RARAReward_v5` там нет, цепочка охватывает `QuantumZScoreReward`,
`HoldAwareReward`, `TradingReward` (`src/apexfx/env/forex_env.py:461,483,507`).

`src/_v2_dump/` — read-only снимок шести файлов для внешних инструментов, не
импортируется ничем в `src/apexfx`, `scripts` или `tests`.

## 6. EWC-консолидация — no-op, логирующий успех

`trainer_v2.py:612-619`:

```python
def _consolidate_ewc(self, stage_idx: int) -> None:
    """EWC Fisher consolidation after stage completion."""
    try:
        from apexfx.training.ewc import EWCRegularizer
        # Simple consolidation: snapshot current params as important
        logger.info("EWC consolidation", stage=stage_idx)
    except ImportError:
        pass
```

`EWCRegularizer` импортируется, но не создаётся; функция пишет в лог «EWC
consolidation» и выходит. Настройка `ewc_lambda` 5000 → 2000 между прогонами не
влияла ни на что, но в логах выглядела работающей.

Следствие для интерпретации: вывод Run 5 «EWC + adversarial закостенил политику
→ 0 trades» верен наполовину — EWC не работал, окостенение целиком относится к
adversarial-стадии.

## 7. Конфигурации могли не применяться

Обнаружено в Run 6 (`a7b611e`): `trainer_v2` использовал hardcoded
`CurriculumV2Config` из `src/apexfx/training/config.py` и **не читал
`configs/training.yaml`**. Run 6 пришлось убить и перезапустить после ручной
правки `config.py`.

Это означает, что описания конфигураций прогонов 1–5 в хронологии могут не
соответствовать фактически исполнявшимся параметрам. Проверить постфактум
нельзя — нужно сверять по логам каждого прогона отдельно.

## Что из этого следует для Run 7

Порядок отличается от плана в `AUDIT_REPORT.md`, где этап A — починка награды и
фильтров. Чинить награду при сломанном измерителе преждевременно: результат
починки будет не виден.

| # | Действие | Обоснование |
|---|---|---|
| 1 | **Считать `sharpe` и `profit_factor` из реализованного PnL эпизода**, не из наград | Без этого Run 7 даст такой же нечитаемый лог. Объём — десятки строк |
| 2 | **Убрать `profit_factor` из early-stop** до п. 1 | Тождественный ноль обрывал стадии на 18–27 % бюджета |
| 3 | **Определить ветку для Run 7** | Мердж `v2.0-quantum-hybrid` → `main` нетривиален (24 коммита, конфликтующие reward-модули), но иначе теряются либо фиксы аудита, либо фиксы прогонов |
| 4 | **Форсировать экспозицию** (`min_position_scale`, `uncertainty_weight`) | При нотионале 0.05 % капитала эксперимент неинформативен независимо от качества политики |
| 5 | Сменить критерий отбора чекпоинтов с `sharpe` на финансовую метрику | Иначе `best_*` продолжит выбираться по бессмысленному показателю |
| 6 | Только затем — baseline vs buy & hold и walk-forward | Этапы B–C плана аудита |

Замечание к п. 6: reality-check аудита остаётся в силе независимо от всего
вышеизложенного — в окне Feb 2024 → Feb 2026 buy & hold по EURUSD даёт +9.97 %
при Sharpe 0.65, и система должна сначала перестать проигрывать этому
ориентиру.
